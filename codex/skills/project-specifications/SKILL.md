# Проектные спецификации

Используй этот навык только когда документация сама является результатом, в репозитории уже действует spec-процесс либо большая многоэтапная работа требует долговечной координации. Обычная реализация, исправление, продолжение и отчёт о состоянии не требуют scaffolding.

## Маршрутизация

Сначала определи режим по корневому `CLAUDE.md` и `specs/master/ACTIVE_STAGE.md`:

- отдельная строка `PROJECT_ORCHESTRATION_MODE: GAME_MASTER_PLAN` включает Game Master Plan;
- `PROJECT_ORCHESTRATION_MODE: STANDARD_DEEPSETING` явно выбирает обычный режим;
- без объявления sentinel `specs/master/ACTIVE_STAGE.md` включает Game Master Plan;
- неизвестное или несколько объявлений — ошибка конфигурации.

В `GAME_MASTER_PLAN` следуй [внешнему протоколу](references/game-master-plan.md). Не создавай параллельные `docs/SPEC.md`, `docs/features/`, `docs/plan.md` и корневой `PROGRESS.md`, если Master Plan их явно не требует.

## Обычный режим

1. Сначала используй существующие документы и их структуру.
2. Создавай новый документ только когда он помогает нескольким этапам или будущим сессиям.
3. Для локальной функции достаточно одного короткого brief в принятом репозиторием месте. Шаблон `templates/feature-brief.md` — опциональная заготовка, а не обязательный формат.
4. Фиксируй только устойчивые сведения: цель, границы, важные решения, проверяемый результат и открытые вопросы.
5. ADR создавай для долгоживущего архитектурного решения; roadmap — для последовательности этапов; handoff — при реальной передаче работы.

Не требуй фиксированный набор документов, отдельное подтверждение критериев, выполнение строго по одному пункту или обновление прогресс-файла после каждого шага. Если пользователь уже поручил работу, документация не должна останавливать реализацию.
