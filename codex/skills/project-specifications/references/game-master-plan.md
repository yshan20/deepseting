# Game Master Plan: работа внутри внешней оркестрации

`specs/master/` определяет КОГДА разрешена работа; `specs/labs/<lab>/` определяет КАК
реализовать подсистему. Явные инструкции репозитория имеют приоритет. Этот режим не заменяет
Master Plan и не создаёт второй источник истины или отдельную базу памяти deepseting.

## Восстановление работы и контекста

При старте прочитай корневой `CLAUDE.md`, `ACTIVE_STAGE.md`, активный Stage и активную Wave,
`CURRENT_STATE.md`, `HANDOFF.md`, релевантные Lab PROGRESS/TODO/task, исходники и тесты.
Следуй `SESSION_START_PROTOCOL.md`, `MEMORY_ARCHITECTURE.md` и другим протоколам репозитория,
когда они есть. Пути Stage/Wave/Lab бери из файлов, не угадывай имена.
Не загружай по умолчанию все 18 Lab specs, будущие stages/tasks и несвязанные документы:
Stage/Wave служат также маршрутизатором контекста.

До существенных изменений восстанови ACTIVE STAGE, ACTIVE WAVE, ACTIVE LAB, ACTIVE MILESTONE,
LAST COMPLETED, CURRENT PLAYABLE BUILD, CURRENT BLOCKERS, NEXT ACTION. Неизвестное состояние
проверь; не придумывай завершённость и сборки. При расхождениях порядок проверки свидетельств:
тесты/реальная сборка → код → Master Plan state → утверждённые контракты/решения →
Lab progress/tasks → current-state/handoff → история разговора последней.
Работающий код подтверждает факты, но сам по себе не разрешает выход за Stage/Wave.

«continue», «go on», «next», «дальше», «продолжай», «давай», «хуярь дальше»:
восстанови ACTIVE_STAGE → активный Stage → активная Wave → HANDOFF → Lab PROGRESS/TODO → task;
продолжай самый ранний незавершённый разрешённый milestone. Не перекладывай выбор Lab/milestone
на человека, если файлы дают ответ. При отсутствующем/противоречивом состоянии исследуй связанные
файлы; спрашивай только о существенном решении, которое так и не удалось восстановить.

## Утверждённая работа

Повторное human approval не нужно, только если выполнены все условия:

- milestone разрешён текущим Stage;
- task включена в текущую активную Wave;
- Lab task существует;
- критерии готовности уже заданы;
- нет блокирующего нерешённого архитектурного или продуктового решения.

Это не разрешение на будущие Wave и не автоматическое продвижение Stage.
Не создавай параллельные docs/SPEC.md, docs/features/, docs/plan.md, корневой PROGRESS.md,
если Master Plan явно не требует их. Не запускай стандартное scaffolding автоматически.

## Классификация решений до вопроса пользователю

| Уровень | Решение | Действие |
| --- | --- | --- |
| 0 | Helper, коллекция, разделение файла, имена методов, private-классы, локальная обработка ошибок | Самостоятельно в утверждённой задаче. |
| 1 | Внутреннее устройство Enemy evaluator / Animation adapter, cache, test fixtures | Самостоятельно внутри Stage/Wave/Lab spec и cross-Lab контрактов. Зафиксируй долговечное решение, если следующий агент мог бы разумно выбрать иначе. |
| 2 | Cross-Lab контракт: поля MotionIntent, семантика событий, save-facing stable IDs, authoritative ownership | Совместимое расширение возможно самостоятельно только при всех условиях ниже. Ломающее или семантическое изменение — архитектурное предложение и approval по Master Plan до реализации. |
| 3 | Multiplayer, модель боя, first/third person, новый pillar, persistent-state architecture, выход за Stage/Wave, массовый контент до Vertical Slice | Останови зависимую работу, создай предложение и запроси явное одобрение. Не принимай решение самостоятельно. |

Условия автономного совместимого изменения уровня 2: расширение уже разрешено текущими specs,
обратная совместимость сохранена, потребители известны, INTERFACE_REGISTRY.md обновлён,
тесты покрывают потребителей, текущая Wave разрешает все затронутые Labs.
Если условия не соблюдены — подготовь предложение по протоколу проекта до изменения контракта.

## Durable memory и завершение сессии

Контекст модели — рабочая память; долговечное состояние хранится в файлах проекта.
Перед reset/compaction/концом сессии выполни `CONTEXT_CHECKPOINT_PROTOCOL.md`, если он есть.
По фактическим изменениям обнови Lab PROGRESS.md / TODO.md, CURRENT_STATE.md, DECISION_LOG.md,
INTERFACE_REGISTRY.md, HANDOFF.md. Не создавай отсутствующие файлы только ради списка:
следуй принятому протоколу. Проверь Git status/diff и зафиксируй результат согласно разрешённому
Git workflow. Решения и блокеры записывай там, где их ожидает Master Plan.

Во всех режимах остаются доменная архитектура, явные границы, отсутствие скрытой связанности,
обобщаемые решения, поддерживаемость, реальные тесты, Git hygiene и проверяемые свидетельства.
Не объявляй заглушки готовыми и не подгоняй решение под отдельную фикстуру.
