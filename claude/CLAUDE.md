# Глобальные правила разработки

Эти правила действуют для всех проектов и всех сессий Claude Code. Применяй их при написании кода и документации.

## Project Orchestration Router

В начале работы найди корень репозитория и прочитай его `CLAUDE.md`. Явные правила
репозитория имеют приоритет над глобальным процессом. Определи режим до создания файлов:

1. Отдельная строка `PROJECT_ORCHESTRATION_MODE: GAME_MASTER_PLAN` включает `GAME_MASTER_PLAN`.
   Явная `PROJECT_ORCHESTRATION_MODE: STANDARD_DEEPSETING` выбирает стандартный режим даже при sentinel.
2. Без объявления наличие файла `specs/master/ACTIVE_STAGE.md` включает `GAME_MASTER_PLAN`.
3. Иначе — `STANDARD_DEEPSETING`; существующий процесс спецификаций и утверждения критериев сохраняется.

Объявление чувствительно к регистру; пробелы по краям допустимы. Не размещай отдельные строки
объявлений в примерах корневого `CLAUDE.md`: они тоже считаются объявлениями.
Неизвестные или несколько объявлений — ошибка конфигурации: не запускай scaffolding до исправления.

В `GAME_MASTER_PLAN` каталог `specs/master/` определяет КОГДА разрешена работа,
а `specs/labs/<lab>/` — КАК реализуется подсистема. Не создавай и не поддерживай параллельные
`docs/SPEC.md`, `docs/features/`, `docs/plan.md`, корневой `PROGRESS.md`, если сам Master Plan
явно не требует их. Не запускай стандартный `new-project.ps1` автоматически и не ставь
конфликтующий specification hook.

Для «continue», «go on», «next», «дальше», «продолжай», «давай», «хуярь дальше» восстанови
`ACTIVE_STAGE → активный Stage → активная Wave → HANDOFF → Lab PROGRESS/TODO → задача`.
Продолжай самый ранний незавершённый разрешённый milestone; не спрашивай заново, какой Lab выбрать.
Задача уже утверждена, если milestone разрешён Stage, включён в активную Wave, существует Lab task
с критериями готовности и нет блокирующего нерешённого архитектурного/продуктового вопроса.
Для такой задачи повторное подтверждение перед каждым milestone не требуется.

Границы автономности, durable memory и загрузка контекста описаны в
`skills/project-specifications/references/game-master-plan.md` относительно каталога этих глобальных
правил. Прочитай этот документ в Game Master Plan режиме до существенных изменений.
Архитектурная дисциплина, явные границы, обобщаемые решения, поддерживаемость, реальные тесты
перед отчётом о готовности, проверка Git diff/status и фиксация решений действуют в обоих режимах.
Сначала исследуй существующий код; не выдавай заглушки за завершённую работу.

## Уточнение задачи перед реализацией

- В `GAME_MASTER_PLAN` сначала классифицируй решение по уровням 0–3 из compatibility reference;
  задавай вопросы только о существенном выборе, который не разрешается файлами проекта.
- Следующие правила уточнения применяются к `STANDARD_DEEPSETING`.
- Прежде чем приступать к реализации неоднозначной задачи, задай пользователю уточняющие вопросы.
- Задавай по пять вопросов за раз, от самых важных к менее важным.
- К каждому вопросу поясняй, что может пойти не так без ответа.
- Останавливайся, когда оставшиеся вопросы перестают влиять на результат.

## Доменная архитектура

- Структурируй код по доменам (предметным областям), а не только по техническим слоям (контроллеры, сервисы, модели и т. п.).
- Группируй файлы так, чтобы любой агент мог понять назначение кода, читая один домен целиком, без необходимости просматривать весь проект.
- Используй явные имена и понятные границы модулей, минимизируй скрытые зависимости.

## Структура проекта — корень

- В корне каждого проекта всегда создавай файл `README.md` с кратким описанием структуры проекта.
- В нём кратко описывай: назначение проекта, список основных каталогов и что в них находится, а также как запускать, собирать и тестировать проект.

## Подробные описания в подпапках

- В каждой ключевой подпапке направления (например, `frontend`, `backend`, `tests`) держи подробное описание этого направления — отдельный `README.md` внутри подпапки.
- Особенно подробно описывай тесты: какие тесты существуют, как их запускать, что они покрывают и как их расширять.

## Спецификации проекта

Проект ведётся по спецификациям: полные инструкции и шаблоны — в скилле `project-specifications`. Загружай его через Skill при старте проекта, начале новой функции и возврате к работе.

## Обобщаемость

- Решение должно обобщаться на невидимые случаи и не должно быть подогнано под какой-либо набор примеров или фикстур.
- Элегантная архитектура — это не эстетика, а способность обобщаться.
- Если существующий тест кажется неверным — не править его, а записать блокер и продолжить с остальным разрешённым объёмом.
- В `STANDARD_DEEPSETING` блокеры и самостоятельные решения фиксируй в корневом `PROGRESS.md`
  («Заблокировано» / «Решения без указания»). В `GAME_MASTER_PLAN` используй Lab PROGRESS/TODO
  и `DECISION_LOG.md` по протоколу проекта; отдельный корневой прогресс не создавай.

## Формат ответов

- Shell-команды выдавай одной строкой, без переносов через `\` и без обратных кавычек-продолжений — так их можно скопировать целиком.
- Пути в ответах указывай в формате `файл:строка`, чтобы по ним можно было перейти из терминала.
